# 文档体系落地质量：最终检视报告（已复核）

> 
> **最终交付版本**：真实性复核的修正、降级、反证边界和新增遗漏已全部合并到本文正文，无需对照另一份复核报告。保留 D01—D37 原身份（D14 为建议），新增遗漏编为 D38—D41。

## 结论

**REQUEST_CHANGES：不能认定原方案已完整落地。** 最优先问题是生成器可截断含手写正文的整个目标；其次是生产影响分析尚未实现、关键消费者仍绕开统一解析、取消结果被当成功，以及 CI 选择/演习证据与承诺不等价。当前全量文档检查也实际为红。

**40项问题：P1 × 1、P2 × 19、P3 × 20；另1项非阻断建议。** 包含确定实现缺陷、文档/设计冲突、已披露验收差距、测试保护缺口和当前检查失败，**不等于40个均已复现的生产故障**。阻断的是“原方案完整落地”的验收及不安全原位生成的启用，不据此宣称全部业务不可发布；本报告也不保证已穷尽所有遗漏。

检视基准为用户指定的[完整方案 F4](../../../.copilot/session-state/44496fd6-bdf0-423c-ae75-8659c1b4a66a/files/documentation-system-full-audit-and-redesign-2026-11-13.md)，核对 F01—F22、C01—C15、AC01—AC20、LA01—LA18。当前为无 Git 历史的归档现场，以下是**当前符合性缺陷/验收缺口**，不推定全部由本次修改引入。仅写入本报告和审阅会话证据，不修实现、不安装依赖、不访问远端或真实数据库。

## 一、直接取证的问题

### D01 · P2 · 单写入源只迁了部分视图，核心规则与路由仍须双写

- **证据**：[redlines.yml](../docs/governance/redlines.yml#L1)仍自称规则表的 YAML 镜像，[修改规则](../docs/governance/redlines.yml#L37)明确要求同步修改 CLAUDE；[canonical-topics.yml](../docs/governance/canonical-topics.yml#L16)同样要求同步手写决策树。[CLAUDE 的权威表](../CLAUDE.md#L32)、[规则正文](../CLAUDE.md#L127)仍承载旧正本。[1.10.0 发布记录](../docs/governance/ruleset-changelog.md#L13)明确写着“§1.8 决策树与 §3 红线不动”，却已把来源切换版本记为完成。
- **失效场景**：只在原方案指定的 YAML 作者处修改规则判据或路由，还必须手改旧正文。新目录和视图生成不等于事实单源化；一致性检查能发现不同步，也不等于生成器能从一个作者源重建。
- **影响**：F22 / T6 / AC03 的核心收益没有实现；后续维护者仍须判断两个互称正本的文件。这里指的是**双写责任未消除**，不是声称所有现有规则值已经漂移。
- **补充量化证据**：真实注册表对 CLAUDE 只生成 executive/self-check，不生成规则表/任务表。CLAUDE 为234行、31,692字节，未达到 F4 §4.2 的原生入口≤10行；AGENTS 为84行、9,714字节，满足其120行/12KiB，不能把两者一起判失败。
- **最小修复**：完成剩余消费者迁移，将规则判据/路由事实的编辑权明确交给各自 YAML；旧入口改成引用或登记的生成兼容视图。同步修正现行权威声明、修改说明及版本完成条件，不重写历史 ADR Decision。
- **验收**：分别只改一次规则描述、一次 topic 入口，运行生成后所有现行消费者一致；不允许通过再手改 CLAUDE 才转绿。只改派生副本必须失败。**置信度：高。**

### D02 · P2 · C14 只覆盖部分取消通道，`SyncResult(cancelled)` 仍被当成成功或失败

- **生产入口**：[UI 日更](../ui/viewmodels/data_source_view_model.py#L469)拿到结果后只看失败表，不判断 `status=cancelled`；失败表为空时发成功通知，并[返回完成消息](../ui/viewmodels/data_source_view_model.py#L523)。[任务执行器](../services/task_manager.py#L973)在任务未预先置 CANCELLED 时把正常返回转成 COMPLETED。
- **第二处消费者**：[补偿循环](../utils/scheduler_service.py#L1040)只在进度回调拒绝或抛出真实取消异常时设置 `cancelled=True`。若第二天通过共享结果标记取消，循环继续，最终走 [TaskIncompleteError](../utils/scheduler_service.py#L1127)；`failed_dates` 为空又使已成功第一天的水位未保存。生产同步层确实存在这种[标记 cancelled 并正常返回的分支](../data/sync/historical.py#L900)，不是假造结果协议。
- **已复现**：提取未经修改的生产函数 AST，以受控 IO 替身执行；同时提取生产 `is_complete` 属性。结果：

| 输入 | 实际结果 | 应有结果 |
| --- | --- | --- |
| UI 收到 `status=cancelled`，失败表为空，任务仍 RUNNING | 返回 `ds_daily_update_done`；发 `snack_full_sync_done_simple / success` | 取消终态，无成功提示 |
| 补偿 d1 成功、d2 通过结果标取消 | 抛 `TaskIncompleteError`；仍访问 d3；水位为空；记录一次失败退避 | 停在 d2，取消终态，保存 d1 合法水位，不记普通失败退避 |
| 对照：d2 抛真实 `CancelledError` | 异常传播，水位保存 d1，失败退避 0 次 | 与当前对照一致 |
- **根因**：新增 [TaskCancelledError 协议](../services/task_manager.py#L152)和[崩溃重建适配](../services/task_rebuild.py#L54)，不等于所有提交方已经消费协作取消结果。现有[两批取消回归](../tests/unit/test_scheduler_service.py#L4053)测试的是“回调返回 False”与“抛异常”，缺少同样被 C14 明确允许的“结果对象标取消”。
- **反证边界**：[TaskManager 直接取消](../services/task_manager.py#L719)会预先置 CANCELLED 并取消 asyncio task。确切问题是“收到合法 cancelled 结果、未提前置终态”这条协议分支处理错误，不能说所有用户点击取消都会误完成。
- **文档同根残留**：[同步规范](../docs/patterns/data-sync.md#L59)、[完成门](../docs/patterns/data-sync.md#L91)、[操作步骤](../docs/guides/how-to.md#L77)仍把主动退出一概要求为 raise。应区分协作结果与真实取消异常，不能为补提交层适配而取消原本允许的统计返回。
- **最小修复**：由业务提交适配器检查取消结果并抛取消信号，TaskManager 继续保持通用异常协议。补偿循环在发现结果取消时停止，复用取消收敛路径保留连续成功水位；UI/调度日更须先区分取消，再判完整/部分/失败。
- **验收**：三种取消通道分别测 UI、调度及补偿提交链，断言任务与持久化终态 CANCELLED、无成功提示、d1 水位保留、不跨 d2、不启动 d3；真实取消异常继续传播。AST 替身复现不冒充真实 TaskManager/数据库集成通过。**置信度：高。**

### D03 · P2 · 唯一当前账本仍是“全部未实施”，与 D13 交接结论互斥

- **证据**：[当前入口](../Plans.md#L2612)仍写“新机制尚未落地”；[唯一任务表](../Plans.md#L2623)T1—T13 共 13 项全部 `cc:TODO`，[表后说明](../Plans.md#L2638)明确全部 TODO 表示未实施。与此同时，[正式维护指南](../docs/guides/documentation-maintenance.md#L171)声称 D13 已完成 30 例演习、655 passed、旧入口 429 passed，且已有首次 CI 修复结果。
- **影响**：读者无法从被指定为唯一当前账本的位置判断哪些已做、哪些受阻、哪些须复核；跨会话继续执行可能重复启动已落地任务。T10 逐项 AC/LA 实证或准确受阻状态没有在该账本收口；这是当前记载互斥，不证明实际工作从未执行，不能拿指南的一段总数代替。
- **最小修复**：沿原 T1—T13 身份记录实际状态、当前输入指纹、对应命令结果及受阻范围；若实施用了 D 编号，给出明确映射，不另建第二本长期账本。保留历史规划原话，但从当前状态中移开。不能将全部状态机械改为完成。
- **验收**：任取 T4/T8/T9/T13 和一个受阻能力，可从当前入口定位相应证据、运行范围及剩余门；任务状态与正式指南一致，不把本地模拟签成远端/产品通过。**置信度：高。**

### D04 · P3 · 正式决策与维护正本的关键来源无法定位

- **证据**：[ADR-0018 来源](../docs/adr/0018-documentation-single-source.md#L6)与[维护指南来源](../docs/guides/documentation-maintenance.md#L5)都指向不存在的 `reviews/文档体系检视与改进.md`，并继续按其章节引用 F/C/T/LA。当前实际可读取的批准方案是用户提供的会话制品，二者之间没有准确定位关系。
- **影响 / 反证**：新维护者不能按所列来源定位相同的原裁定、授权边界和验收定义，内联代码路径也不自然进入 Markdown 链接检查。但 ADR 已承接大量裁定，不能说决定正文也缺失；问题限于来源定位和交付便携性。
- **最小修复**：记录准确的来源制品标识、文件名、内容 hash 与适用版本，修正现行引用。保留报告不入库的边界，**不要为修来源定位而把检视报告提交到正式规范目录**。
- **验收**：在另一份归档/有效 clone 中，读者能按来源定位规则取得相同合同，或得到明确的“外部证据不可用”状态，不再把不存在的路径当证据。**置信度：高。**

## 二、规范、操作与示例的残留冲突

### D05 · P2 · 例外注册表已禁止扩展，新增服务入口仍要求继承豁免

- **证据**：[应用服务规范](../docs/patterns/application-service.md#L24)、[完成门](../docs/patterns/application-service.md#L52)、[新增服务操作](../docs/guides/how-to.md#L394)仍要求新增轮询服务“复用此豁免语义”；但 [EX-0017](../docs/governance/exceptions.yml#L209)、[EX-0018](../docs/governance/exceptions.yml#L220)已限定既有方法/流程，不扩展到新方法、新服务。
- **影响**：F01 的 AND 谓词本身已修，真实开发入口仍把特定批准扩成通用许可。原获批路径不是本项问题，不应反向全部取消例外；未证明已有新服务实际违规。
- **修复 / 验收**：入口改为核对具体登记范围及全部有效条件；新增服务须另按规则判断，不能自动继承。测试或语义用例必须同时证明“原登记方法可沿用”和“新服务不可沿用”。**置信度：高。**

### D06 · P2 · MVVM 正例导入真实 VM，却调用不存在的示例 API

- **证据**：[MVVM 正例](../docs/patterns/mvvm.md#L78)与 [Flet 正例](../docs/flet/v1-api-constraints.md#L143)导入真实 ScreenerViewModel，却使用 `vm.run()` / `state.status`；真实入口为 [run_strategy](../ui/viewmodels/ai_stream_mixin.py#L761)，状态字段为 [status_message](../ui/viewmodels/screener_types.py#L224)。
- **影响 / 反证**：前面的抽象骨架确实定义 run/status，但随后重新导入的生产组合类/MRO 没有 run 别名，Flet 文档还称该段为唯一 canonical 示例，因此不能用“纯伪代码”免责。是可复制文档示例错误，不是生产 View 已运行失败；仅替换名称也不够，还须处理命令参数与可空状态。
- **修复 / 验收**：要么从构造参数到字段/command 全部使用生产 API，要么改成明确独立的 Demo VM。应用环境实际渲染并触发一次事件；仅验证导入符号存在不足以发现此问题。**置信度：高。**

### D07 · P3 · 随包恢复说明仍把保全条件错误绑定到 exit 20

- **证据**：[随包说明](../resources/maintenance/README-maintenance.md#L93)及[退出码说明](../resources/maintenance/README-maintenance.md#L108)仍让 exit 30 看起来会在非切换失败时自动清理；而 Rust [恢复失败后停止也失败](../sidecars/qtrading-pg-sidecar/src/maint.rs#L1576)时保留原恢复错误码并置 `preserve_dir=true`，由[清理分支](../sidecars/qtrading-pg-sidecar/src/maint.rs#L1437)保留目录。因此存在 **exit 30 且必须保留目录** 的真实分支。
- **影响 / 反证**：失败码与保留目录的对应关系错误，影响故障分流。顶部已有保留回滚目录的总警告，运行时也会告警，故不把此项夸大为“完全无保全提示”或已发生误删。how-to 已补[双失败分支](../docs/guides/how-to.md#L186)，仍应同步随包说明。
- **修复 / 验收**：按“停止是否已证明”决定是否可清理，而非只按 exit 20。分别核普通恢复失败、恢复与停止双失败、切换失败；停止未知时一律不切换、不清理、不报成功。**置信度：高。**

### D08 · P3 · 检视 profile 继续引用未定义的全局 100ms 阈值

- **证据**：[R16 人工追查](../docs/reviews/review-profiles/project-profile.md#L38)仍以 `>100ms / ≤100ms` 作统一分界，并引用 [CLAUDE §3.2](../CLAUDE.md#L180)；后者没有定义这个全局数值，原方案 C10 已明确要求删除该背书。
- **影响 / 反证**：数值背书与 C10 不符，可能混淆评审标准。但同段允许对象已限定为短小非阻塞计算，前文禁止同步阻塞 IO，不能说规范明确放行低于100ms的同步IO。
- **修复 / 验收**：使用执行线程、阻塞性质与不可控依赖判断；PerfThreshold 只作慢操作告警。用一次采样很快、但耗时无界的同步 IO 作禁止例，用真正短小计算作允许例。**置信度：高。**

## 三、Agent 公共合同没有贯穿活消费者

以下同时核对附件与当前 Cursor 消费链；历史 backup 不要求同步为当前，更不据文档冲突断言生产 Agent 已发生错误。

### D09 · P2 · HANDOFF 事件唯一键仍误用已提交水位

- **证据**：[附件 HANDOFF](../agent-design/AGENT_TECHNICAL_HANDOFF_v1.4_2026-11-10.md#L146)、[当前 HANDOFF](design/AGENT_TECHNICAL_HANDOFF_v1.4_2026-11-10.md#L146)仍写公开事件键 `(execution_id,event_seq)`；但[当前 DD 事件表](design/AGENT_SYSTEM_DETAILED_DESIGN_v1.4_2026-11-11.md#L1475)使用 `session_seq/execution_seq`，唯一键为 `(execution_id,execution_seq)`；`event_seq` 是所属对象的已提交水位。
- **影响 / 修复**：照交接实现会引用错误列或混淆事件身份与快照水位。逐处改事件键与游标说明，不迁水位列、不新增事件表。
- **验收**：同会话多执行交错产生事件，包络、去重键、查询游标与物理唯一键一致；会话序列和执行序列分别校验。对应 C01 / AC10。**置信度：高。**

### D10 · P2 · 三身份只改到部分存储描述，请求/回执/投递仍有含糊别名

- **证据**：[当前 DD](design/AGENT_SYSTEM_DETAILED_DESIGN_v1.4_2026-11-11.md#L304)明文不使用含糊 `command_id`，但 [CommandRef](design/AGENT_SYSTEM_DETAILED_DESIGN_v1.4_2026-11-11.md#L428)、[DraftReceipt](design/AGENT_SYSTEM_DETAILED_DESIGN_v1.4_2026-11-11.md#L442)仍列该字段；[HANDOFF 接口](design/AGENT_TECHNICAL_HANDOFF_v1.4_2026-11-10.md#L71)、[答复投递](design/AGENT_TECHNICAL_HANDOFF_v1.4_2026-11-10.md#L153)、[撤销](design/AGENT_TECHNICAL_HANDOFF_v1.4_2026-11-10.md#L285)、[DBOS 幂等键](design/AGENT_TECHNICAL_HANDOFF_v1.4_2026-11-10.md#L395)也有残留；附件 HANDOFF 对应位置同样存在。
- **影响 / 反证**：接口实现者仍须猜客户端幂等键还是持久记录 PK，跨目标复用客户端键时可能错误关联回执。物理表、客户端身份和消息→来源派生已有正确规定，不能说三身份全部未实现，也未证明现存 Agent 数据库已经串单。
- **修复 / 验收**：按用途区分 business_request_id、client_command_id、command_record_id，不全局替换。覆盖同键同目标重传、同键异目标、同意图异输入、队列修订与丢回执；请求方不得指定持久 PK。对应 C02 / AC10。**置信度：高。**

### D11 · P2 · 成果消费者仍从 `kind=plan` 推出“未执行”

- **证据**：[当前 DD 成果摘要](design/AGENT_SYSTEM_DETAILED_DESIGN_v1.4_2026-11-11.md#L467)、[当前 HANDOFF](design/AGENT_TECHNICAL_HANDOFF_v1.4_2026-11-10.md#L632)、[当前 UX](design/AGENT_UX_DESIGN_SCENARIO_v1.4_2026-11-03.md#L258)仍要求计划另标“未执行”，而 [ADR C07](../docs/adr/0018-documentation-single-source.md#L48)规定状态来自关联执行，未知显示未知。
- **影响 / 反证**：[后补现行合同](design/AGENT_UX_DESIGN_SCENARIO_v1.4_2026-11-03.md#L811)已明确计划类型不等于永远未启动；UX 中“仅计划交付后尚未启动”的合法场景应排除。残留是成果目录等活摘要未收口，不是全体系都错误，也未验证真实 UI 误显；实现这些旧摘要仍会得到与关联执行事实冲突的映射。
- **修复 / 验收**：成果类型和执行事实分别消费；覆盖未启动、排队、运行、终态、关联未知，启动所审版本产生新意图而重传不重复启动。对应 C07 / AC10。**置信度：高。**

### D28 · P1 · 原位写入先截断、单次 write 不检查短写，可损坏整个目标正文

- **证据**：[WriteGuard.write_bytes](../scripts/docs_generated.py#L1127)先 `ftruncate(fd, len(data))`，再单次 `os.write`，未循环处理短写或核对返回字节数；[run_update](../scripts/docs_generated.py#L1304)随后把目标记为已写。写入的是整个文件，不只是派生块，目标可含 AGENTS 等手写正文。

- **验收**：短写、截断后异常、提交中断三类负例，均断言原正文完整、退出非零、已写/未写准确；未验证真实断电/杀进程，不宣称做过。对应 AC07 / LA11。**置信度：高。**

### D29 · P2 · 独占保护没有覆盖真实动态作者源，all 检查也在释放保护之后

- **证据**：[文件发现](../scripts/docs_generated.py#L661)、[索引渲染](../scripts/docs_generated.py#L717)读取 docs 树的标题/角色及 ADR 内容，但[注册表](../scripts/docs_generated.py#L899)的 `docs-readme-adr-index.sources=()`；[更新入口](../scripts/docs_generated.py#L1231)只快照登记的少数文本源，普通文档、ADR 内容及目录成员变化不在 source_snaps/guard_paths。all 回调在退出 WriteGuard 后调用。
- **影响 / 反证**：已登记源确有内核独占保护，不能称完全无保护；漏的是动态docs/ADR文件及目录成员闭包。[DEV-01](../docs/adr/0018-documentation-single-source.md#L90)已明示保护外检查，属于已披露但原合同未满足的验收差距。事后重渲染可能检出最终差异，不能据此证明提交时源快照稳定，也不能断言每次并发编辑必然逃检。
- **修复 / 验收**：先计算真实作者文件及目录成员集合，快照并纳入保护；检查复用受保护快照/句柄。以真实内置注册表在渲染后修改普通文档/ADR、增删成员，证明可靠串行化或冲突退出；无法证明的平台拒绝原位更新，不能只测所有源都显式登记的 demo registry。**置信度：高。**

### D30 · P3 · 从已反转义文本恢复引用语法，合法转义文字误报

- **证据**：[_collect_unresolved](../scripts/docs_markdown.py#L411)逐 text token 正则匹配；token 已失去原始转义来源，强调又将候选拆成多个 token。
- **生产解析器内存反例**：`\[ok\]\[undefined\]`是真链接0却报错1。原报告将`[**x**][undefined]`不报称作漏链不成立：CommonMark把未定义引用形态当普通文字；已定义但目标缺失的格式化引用当前可正确失败。
- **修复 / 验收**：保留原始转义语境，避免从显示文本倒猜语法；不得扩大正则去拒绝合法的格式化普通文字。转义文字允许，已定义缺目标引用拒绝，围栏/行内代码保护保留。对应AC05/LA10。**置信度：高。**

### D31 · P2 · URL 处理分支不一致，HTML href 不进入链接检查

- **证据**：[链接检查](../scripts/check_docs_consistency.py#L404)对无 fragment 的路径分支未统一 URL 处理；[HTML 收集](../scripts/docs_markdown.py)保留原 token/ID，却没有把 href 接入真实检查。
- **生产函数反例**：目标 README 实际存在时，`./README%2Emd` 被误报死链，`./README.md?raw=1` 被当成含 query 的文件名；`<a href="never-exists.md#missing">` 两个链接检查都返回空错误。带 fragment 的部分路径已有解码，不能泛称全无 URL 处理。
- **修复 / 验收**：共享 URL 分类与 path/query/fragment 分离、路径解码；Markdown 内 HTML href 纳入链接视图，或明确输出未核而非静默放过。合法路径通过，HTML 真缺目标/缺锚点失败。对应 AC05。**置信度：高。**

### D32 · P3 · F20 正常对照加了额外标题，避开块外同节正文误报

- **证据**：[_parse_min_verify_command_block](../scripts/check_docs_consistency.py#L2397)把块外同节内容也纳入未知行判断；[正对照](../tests/docs/test_consistency.py#L3930)通过新增“使用说明”标题触发扫描截止。

### D33 · P2 · 同义重复被误叫双义 WARNING，且该 WARNING 直接让 CLI 失败

- **证据**：[对义检查](../scripts/check_docs_consistency.py#L3951)未比较归一化语义集合；[公共收集](../scripts/check_docs_consistency.py#L4572)把该检查的 WARNING 文本直接加入 errors。glossary 专用 warning 包装器没有覆盖它。

### D34 · P2 · 作者源校验只验证键存在，null/空集仍能进入渲染

- **证据**：[_validate_source_items](../scripts/docs_generated.py#L391)及[路由检查](../scripts/check_docs_consistency.py#L2135)未完整校验必填值形态。
- **实证**：内置schema接受空topics、null及空字符串；全null可渲染出 `| None | None | [None](None) | — |`。但保留原合法决策树时，全null/空集会被后续映射检查拒绝，不能称all静默放行。仅title:null仍可过canonical/映射/受检范围三项，说明必填值形态确有校验空白。
- **边界 / 修复**：问题限定为**写前值校验不足**，最终渲染比对是否另拒应分层说。身份、标题、canonical校验非空字符串，路径合法存在，来源集合按职责要求非空，全部在任何写入前完成。
- **验收**：非法源不能进入渲染/写入阶段；不能只断言写完后最终退出非零。对应 AC06/07。**置信度：高。**

### D35 · P3 · 坏输入异常中断独立检查聚合，写后异常还会丢失提交状态报告

- **证据**：[redlines 检查](../scripts/check_docs_consistency.py#L1229)、[聚合入口](../scripts/check_docs_consistency.py#L4572)、[main](../scripts/check_docs_consistency.py#L4648)、[写后回调](../scripts/docs_generated.py#L1335)没有完整的检查域错误收敛/状态报告边界。

- **验收**：前项坏输入、后项仍执行；写后回调异常仍列已写/未写和失败原因。未执行真实写后破坏实验。对应 AC07/08。**置信度：高。**

### D41 · P3 · 替换受控块会改写块外手写部分的混合行尾

- **生产入口**：[replace_block / _join_lines](../scripts/docs_generated.py#L319)使用splitlines后按全文单一换行重组。输入手写头/尾为LF、受控块为CRLF，仅改块内old→new后，头/尾也都变CRLF；纯内存调用生产函数已复现。

- **修复 / 验收**：按原字节/保留行尾的区间替换，不重组无关正文；LF、CRLF、混合及无末尾换行分别断言块外字节完全相同。对应 AC07 / LA11。**置信度：高。**
