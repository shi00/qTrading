### 1. P2｜向导卸载没有调用基类清理，通知状态仍存活

- **问题编号**：`PY-ui.viewmodels.onboarding_view_model / OB-01`
- **代码位置**：[ui\viewmodels\onboarding_view_model.py](../../ui/viewmodels/onboarding_view_model.py)；[dispose](../../ui/viewmodels/onboarding_view_model.py)。
- **哪里有问题**：override只清callbacks/subscribers/状态，不调用super.dispose，也不置notifier disposed。通知内核的disposed守卫、pending通知取消/loop解绑只在基类dispose生效；旧start_sync完成仍执行_set_state(progress=1,done)，已有受控sync测试只断言不导航，未断言state保持默认。已经排队捕获的subscriber快照亦不因clear列表自动无效。
- **造成什么影响**：卸载后state仍会改变，已排队回调可能触及销毁View。
- **原因**：绕过统一notifier关闭协议；不是“同步取消未传播”。

**具体怎么改**

本模块dispose保留验证取消/业务清理，同时调用统一super.dispose关闭notifier，再重置state；处理幂等与服务取消失败，不能漏基类收尾。接口影响：MVVM生命周期及R2、无需取消必须自然完成的落盘操作；边界验证：dispose前排队通知、validator/同步迟到、重复dispose均不复活state或旧回调。无公共接口变化。
  本文件已存在的取消验证API保留，以finally保证通知协议一定关闭：

```
def dispose(self) -> None:
    from services.local_model_manager import LocalModelManager

    self._sync_generation += 1
    try:
        LocalModelManager.cancel_verification_if_active()
    finally:
        super().dispose()
        self.fn_validate_database = None
        self.fn_validate_token = None
        self.fn_validate_model_scenario = None
        self.fn_validate_cloud_ai = None
        self.fn_validate_local_model = None
        self.fn_push_schedule_state = None
        self.on_complete = None
        self._step_validated.clear()
        self._persisted_schedule = None
        self._state = OnboardingState()
```

  不再直接操作notifier的subscriber列表，依赖已实读基类幂等清理；验证取消失败仍传播且不会遗漏本地收尾。

**如何验证**

Given同步/通知已挂起，Whendispose后释放它们，Thendisposed=True、state保持默认、旧subscriber无调用，且不导航。

### 2. P2｜旧同步任务的进度和结果可能覆盖新一轮状态

- **问题编号**：`PY-ui.viewmodels.onboarding_view_model / OB-02`
- **代码位置**：[ui\viewmodels\onboarding_view_model.py](../../ui/viewmodels/onboarding_view_model.py)；[start_sync.progress_callback / 成功失败回写](../../ui/viewmodels/onboarding_view_model.py)。
- **哪里有问题**：run_id只在_complete_sync_success及finally清busy时核验；progress callback、成功done、resultFalse和异常状态无代次检查。已读ControlledSync测试明确允许旧运行在cancel/新同步后返回True；旧运行虽然不导航/不清新busy，仍能把新运行进度改成100%/done。
- **造成什么影响**：“同步中”显示旧运行已完成/错误，取消提示被覆盖。
- **原因**：所有权保护只覆盖导航和busy，没有覆盖进度/错误。

**具体怎么改**

仅本模块所有同步进度/结果/异常回写先核run_id当前代次，导航继续核epoch。接口影响：保持同步自然完成和R2；边界验证：A取消后B启动、A迟到成功/失败/进度均不动B，当前B正常完成仍到schedule。无接口迁移。
  在现有start_sync内定义局部owner判据，无新跨模块API；进度分支和结果await后复用：

```
def owns_sync() -> bool:
    return not self._disposed and run_id == self._sync_generation

def progress_callback(current, total, message):
    if not owns_sync():
        return
    self._set_state(
        sync_progress=current / 100,
        sync_progress_message=Message("wizard_status_syncing"),
    )

dp = await self._ensure_processor()
result = await dp.initialize_system(
    progress_callback=progress_callback, quick=quick
)
if not owns_sync():
    return
```

  原结果分支保留；现有普通异常回写放入 `if owns_sync():`，原finally也使用同一判据。`except asyncio.CancelledError: raise` 无条件保留，不能用owner失败吞取消。局部helper定义已给出，不依赖不存在的服务方法。

**如何验证**

Given两受控运行A/B，WhenA在B启动后回调进度/返回成功，ThenB仍显示B进度，A不得写done；取消后同样保留cancelled。

### 3. P2｜Token 步验证 A 成功 → 到模型步 → 从模型首子步骤返回 Token → 输入 B → 下一步

- **问题编号**：`PY-ui.views.onboarding_wizard / UIV-ONB-01`
- **代码位置**：[ui\views\onboarding_wizard.py](../../ui/views/onboarding_wizard.py)；[`OnboardingWizard` 的 Tushare VM factory](../../ui/views/onboarding_wizard.py)。
- **哪里有问题**：Token 步验证 A 成功 → 到模型步 → 从模型首子步骤返回 Token → 输入 B → 下一步。Onboarding VM 的 `_step_validated["token"]` 仍 True，直接跳过验证，B 不被验证/保存。
- **造成什么影响**：显示草稿与已确认配置不一致，用户以为新的 Token 已生效。
- **原因**：Token VM 没有 on_change 失效回调，重新绑定 validator 不会清缓存。数据库输入已有 invalidate_step 机制，计划草稿亦有对应机制。

**具体怎么改**

仅本文件 factory 传现有 `on_change=lambda: onboarding_vm.invalidate_step("token")`，不修改两个 VM。**规范轮**：沿用数据库同型公开命令、保持 SaveOutcome 与 bool 契约；**对抗轮**：同值刷新不制造重复副作用，空 Token/失败不能推进，修改后取消/返回仍不能复用旧确认。

```
_tushare_state, tushare_vm = use_viewmodel(
    factory=lambda: TushareConfigPanelViewModel(
        show_internal_loading=False,
        on_change=lambda: onboarding_vm.invalidate_step("token"),
    )
)
```

  兼容性：仅使用已核实的 Tushare VM 构造参数与 Onboarding VM 公共命令；不改变向导步骤、validator 返回类型或依赖实现。同值事件若实际到达，最多使缓存失效，不会在事件中立即产生持久化副作用。

**如何验证**

前置条件：A 已验证且返回 Token 步，操作：改 B 并继续，预期结果：再调用 validator，B 失败停留该步；未运行。
