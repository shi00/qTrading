## 3. 模型与场景

### 3.1 产物、宏变量与目录

| 官方矩阵 `variant` | `backend` / `embedded` | spec 输入及 installer 分支 | 目标 |
| --- | --- | --- | --- |
| `cpu` | cpu / false | 通用 dist；排除 sidecars；无 maintenance | standard、外置 PG |
| `cuda` | cuda / false | CUDA CMAKE_ARGS 与独立 uv 缓存；其余同 cpu | standard、外置 PG |
| `embedded-cpu` | cpu / true | 下载 Windows x64 sidecar；通用文件 + sidecars 整目录 + maintenance | 内置 PG |
| `embedded-cuda` | cuda / true | CUDA 构建 + 同一 Windows x64 sidecar 收集路径 | 内置 PG |

- “standard”是产品分类，官方实际宏值是 `cpu/cuda`，并没有第五条 `standard` matrix leg。本地不传宏会落 `unknown`，不能拿它代表发布路径。
- build-windows 为 Windows runner + Python 3.14，`pyinstaller AStockScreener.spec` 输出 `dist\AStockScreener`；`build` 是中间目录，installer 不从 build 取文件。四条 matrix leg 的工作区分别构建，没有在同一 dist 中混合 CPU/CUDA。
- `ArchitecturesAllowed/ArchitecturesInstallIn64BitMode=x64compatible`；sidecar 下载目标明确为 `x86_64-pc-windows-msvc`。没有原生 Windows ARM64 应用构建声明；ARM64 上 x64 兼容运行未实测。sidecar.yml 的 Linux x64/ARM64、macOS ARM64 只是 **sidecar** 独立产物，不等于这些平台已有桌面安装包。
- spec 的 locales/assets/Alembic/tiktoken 缓存收集与 `config.RESOURCE_ROOT`（frozen 为 `_MEIPASS`）一致；四个 Flet hiddenimports 已有。`collect_data_files` 包数据和 `collect_dynamic_libs("llama_cpp")` 已有，不能因使用惰性加载就直接报漏包。
- AppId 固定为 `{7E6D0B44-BD44-4E46-8B5C-3A5F2D237C1A}`，四变体共享；默认每用户 `{localappdata}\Programs\AStockScreener`、`PrivilegesRequired=lowest`。`MyAppVersion` 默认 0.11.3，正式构建被 `/DMyAppVersion=${{ github.ref_name }}` 覆盖；tag 带 v、手动 ref 是分支名，不据此臆断 ISCC 失败，文件版本/显示版本需取真实产物核实。

### 3.2 三种 manifest/hash 不是同一种消费者

1. sidecar.yml `cargo build --target <matrix.target> --release` → **同一个 `matrix.binary_path`**供 `version --json` 和 `compute_sha256` → `sidecar-manifest-<os>.json`。Rust `VersionJson.target` 来自编译 `TARGET`，生成器顶层 target 则来自 CLI；当前 matrix 传值相同，但生成器没有交叉校验（S01）。
2. sidecar Release 将上述 binary **按原字节复制**为平台唯一资产名，生成 `sha256sums-<target>.txt`。Windows 桌面构建仅下载 Windows x64 资产和该 sums，重命名为 `qtrading-pg-sidecar.exe` 后比对实际摘要，缺 sums 或不匹配均失败。JSON manifest 在这段桌面下载流程中没有被下载/消费；不能宣称桌面已校验 JSON 中的版本/target。
3. spec `_stage_sidecar_with_sha256` 对实际待打包 binary 重新求摘要，生成同名 `.exe.sha256`，两者装入 `_internal\sidecars`；EXE/COLLECT 的 strip/upx 均 false。installer embedded 分支递归收集整目录。Python `from_config` 取 `_MEIPASS\sidecars`，`_verify_sidecar_sha256` 取 `.exe.sha256`，frozen 缺失/坏格式/不匹配在 Popen 前失败。

因此**当前静态目标/字节链未发现错配**。Release JSON 的 binary_name 是原始 basename，资产名是平台唯一名，桌面再重命名回来：名称不同不代表字节或目标不同。构建后的 PE/DLL 及安装后目录没有真实样本，端到端一致性仍 unknown。

## 4. 已核实发现

首轮详细记录（历史：接受根因仍有效，暂缓/升级以现行台账为准）

### D17-F02：Windows 默认 PGDATA 的 appauthor 层被安装/维护脚本遗漏

- **类别/严重度/置信度**：defect / P2 / high，完整静态路径；`preexisting_related`，不是版本升级引入判断。
- **位置/契约**：`installer.iss::UninstallRun` 的 `--data-dir`、upgrade/uninstall smoke 的 `$PgDataDir`、running_app Step 6；旁证维护包装器 `DEFAULT_DATA_DIR` 及 README。它们承诺与 service 的 platformdirs默认一致，但 `EmbeddedPostgresService.from_config` 调用 `user_data_dir("qTrading")` **没有 `appauthor=False`**。
- **API实证**：本机安装元数据为 platformdirs **4.11.12**，与 `requirements-dev.txt` 的该项完全一致；只读其 `__init__.py::user_data_dir` 和 `windows.py::Windows._append_parts`，没有导入执行包。签名默认appauthor=None，Windows在appauthor不是False时取author=appauthor或appname，再追加appname。因此无配置覆盖时服务是 `%LOCALAPPDATA%\qTrading\qTrading\postgres\<major>\data`，而installer/smoke/包装器是 `%LOCALAPPDATA%\qTrading\postgres\16\data`。本机真实LOCALAPPDATA值/真实目录未读取。
- **触发与逐跳**：Windows、platformdirs可导入、PGmajor=16、默认配置→service选择两层目录→安装器stop/离线包装器及smoke选择单层目录。服务主程序可以使用自己的数据，但卸载stop指错目标；status/doctor可能报告未初始化，dump找不到主库，upgrade/uninstall检查不到真实数据；running_app可能另建第二个库而不是验证原实例。没有推导“卸载一定删库”或“stop一定成功”。
- **反证**：`config._user_data_dir` 已显式appauthor=False，但这是AStockScreener配置目录，PG service未使用它；Rust Layout只消费传入data-dir，不会替脚本补上遗漏层；自定义数据目录可偶然对齐，但不修复默认行为；crash脚本清理整个qTrading根会包含两层目录，却不证明其他脚本读对路径。若打包机根本缺platformdirs，路径分支尚未到达，另交O02，不把本机API结果当构建启动成功。
- **最小修改/保留接口（未实施）**：保留服务已经使用的两层目录、默认主版本解析、既有配置和用户数据；把installer stop、smoke和随包维护脚本/README的Windows默认映射对齐到同一约定，增加路径契约测试。不要直接给生产service补`appauthor=False`使现有库失联；如果产品决定迁移为单层，须另行设计已有目录检测、冲突拒绝和可回退迁移，不能删除或默默新建空库。自定义目录仍走显式参数。
- **回归输入→期望**：无配置、固定合成LOCALAPPDATA根时，各消费者的默认路径均与 `Windows("qTrading").user_data_dir` 加PG版本一致；旧两层数据加唯一哨兵，升级/卸载/再安装后仍指向原库；只有单层遗留目录或两层同时存在时不静默合并/删除。用应用已有自定义路径时不能误操作默认目录。未来V1补路径断言，V5/V7/V8在VM核实业务哨兵。
- **验证/回退/残余**：独立ntpath模型已验证两种路径不同；没有安装/DB运行输出。回退只撤消费者路径修订，保留原数据；真实卸载活进程/锁行为仍unknown。当前未核验远端sidecar版本，不声称任何已发布安装包已实际发生该问题。此根因由D17登记，D16涉及相同默认目录时引用F02去重。

### D17-F01：独立 sidecar 拦截 smoke 为已有库指定不存在的另一密码文件

- **类别/严重度/置信度**：defect / P2 / high；依据完整可达静态链，不是失败运行截图。历史关系 `preexisting_related`；缺 Git 基线，不声称本次引入。
- **位置**：`scripts\installer_smoke_running_app.ps1` Step 6（116–118）；关联 `sidecars\qtrading-pg-sidecar\src\run.rs::run`（135–157）、`paths.rs::Layout::from_data_dir`、`password.rs::read_password_file`；CI `build-windows` 的 Installer Scripts step（2018–2047）。
- **契约**：脚本要在独立 sidecar 存活时验证 installer 拒绝，且安装尝试后同 PID 仍存活；CI 正本要求该 release-tag smoke 任一步失败即中断发布。
- **触发**：embedded 安装包存在；**Step 6实际传入的PGDATA**已经初始化，且该库真实密码在runtime/password、`fake_sidecar_pwd`不存在。例如应用配置把PGDATA设为脚本当前单层路径，或F02修正后复用应用真实默认库。该假密码文件只有引用，没有创建步骤。默认路径存在F02时，不能直接把“应用已初始化”当成“脚本所指目录为Existing”。
- **逐跳证据**：
  1. `ci_cd.yml` 仅在 embedded + `refs/tags/v*` 依次运行 crash_recovery、running_app，并检查两次 `$LASTEXITCODE`。
  2. running_app 先安装并启动真实应用；Step 6 使用硬编码PGDATA（路径错位见F02），又显式传 `--password-file "$env:TEMP\fake_sidecar_pwd"`。
  3. `Layout::from_data_dir` 显式参数优先，不会回退到已有 `runtime\password`。
  4. `read_password_file` 对不存在路径返回 None；`guard_data_dir` 对健康已初始化目录返回 Existing；`run` 在 Existing+None 分支返回 `PASSWORD_FAILED`（16），发生在 ready/监督前。
  5. 快速返回时 Step 6 的三秒存活断言失败；即便准备工作较慢使其暂时存活，也无法证明已经认证并就绪，后续可能以初始化期进程冒充运行中实例。CI 接受/失败时序需实测，不声称已经观测到某次 Release 失败。
- **当前/预期与影响**：当前可把合法已有库的密码保护误判为运行中安装验证失败，或只测到尚未就绪的进程；预期先建立真实 ready 的 sidecar，再验证安装拒绝且进程/数据不变。影响发布验证可靠性和发布可达性，不是产品密码处理缺陷。
- **反证**：Fresh 分支会生成密码，F02甚至可能使当前默认首跑走另一个Fresh库，因此没有笼统断言“首次发布必失败”；本发现限定输入位置的Existing库。不存在 binary 会显式跳过，但官方 embedded 下载/打包链正是提供 binary。该库真正的密码文件存在也不能挽救显式传错路径。静态测试只保护 GUI 等待、退出码和旧资产命名，没有校验该参数。实际下载latest sidecar的版本未取得，本结论是冻结脚本与冻结sidecar契约不兼容，不是远端某次发布失败实录。
- **最小修改方案（未实施）**：保留脚本 `-InstallerPath`、Step 7/8 拒绝与同 PID 存活断言、installer 宏/AppId、Rust Existing 缺密码返回16的保护不变。Step 6 删除错误的 `--password-file` 覆盖，复用该 data-dir 派生的 runtime/password；以有界进程句柄启动并持有 stdin（例如 ProcessStartInfo 的重定向输入流），解析 ready JSON 后才安装，finally 关闭自己持有的输入/等待指定 PID。不能创建伪密码绕过认证，也不能把拒绝检查改成允许成功。
- **回归输入→期望**：健康 Existing+默认密码→ready 后安装返回非零、同 sidecar PID 保持存活；Existing+缺密码→sidecar16且标记“前置失败”，**不**报告 installer 拒绝通过；Fresh→真实 ready 后同样拒绝；standard→sidecar场景明确不适用而主程序拒绝仍测。脚本静态测试增加不得传假密码文件/保持运行断言，真实行为仍须 VM。

## 5. 待确认、待验证及测试缺口

首轮详细记录（历史：接受根因仍有效，暂缓/升级以现行台账为准）

### D17-T01 · test_gap · P2 · “进程出现”不是 ready，也未验证崩溃后的重启可用性

三个 `Wait-SidecarReady` 仅按名字找到进程即返回；crash 脚本最终断言 sidecar/postgres 消失，不再启动应用/读取原数据。即使 PG 正在 initdb 或稍后认证失败，名称存在也能先给 true。`run::run` 明确在健康检查和 ensure_database 后才输出 ready。缺的是有效运行及恢复验收，不据此认定真实恢复有错。

方案：保留现有退出/无孤儿断言，补 ready JSON 或结构化 status 的真实活性证据；崩溃注入前写已提交合成业务哨兵，退出后重新启动并断言哨兵可读。对“子进程存在但永不 ready/ready 前退出”的输入，预期超时/失败而非通过。180s/30s 的合理上限不以任意缩短代替状态校验。归 D17，进程监督实现由 D16复核。

### D17-T02 · test_gap · P2 · 升级/卸载只有目录非空断言，没有数据连续性证据

upgrade Step 5/7 和 uninstall Step 5/7 只检查目录存在与文件数 >0；升级后再次启动仍只等进程。独立合成反例：删除唯一业务哨兵但保留 PG_VERSION，现有非空谓词仍成立。它证明**断言不足**，不证明安装器实际删数据。两个脚本在 CI 的出现还包括语法检查/静态单测；实际 release Installer Scripts step只调用另两个脚本，不能声称已自动跑过升级/卸载。

方案：同变体旧版建库后写合成哨兵和非秘密配置标记，关闭后升级/卸载→再安装，断言读回原主键/值、版本与配置；记录完整 PG 根目录（data/install/runtime）保留情况，不只 data 子目录。PG 运行后物理文件可能合法变化，不能要求整库字节永远不变。新测试输入“目录非空但业务行缺失”必须失败。旧版 Release可用性/下载须另行确认授权；可先用预置可信离线安装包的新适配入口，不能假定现脚本已有该参数。

### D17-T03 · test_gap · P2 · 产物自检未覆盖动态加载与目标机 DLL

`main::_run_smoke_test` 仅 import app/Flet/Polars 和检查资源目录；不启动 `_persistent_worker`、`_scoring_worker`，也不加载模型/tokenizer、真实 keyring 后端或运行 CUDA。spec 已显式收集 llama DLL，`tokenizers` 还是 litellm 锁文件的传递依赖；第三方 PyInstaller hooks/传递导入能否补齐，**未取实际构建 TOC/产物，不能说必缺 tokenizers/Flet 数据**。

方案：在无构建机 Python/site-packages、无 CUDA Toolkit PATH 注入的隔离目标系统上，分别验四变体；用获批离线合成/测试模型触发两条 worker ready/一轮响应/退出，核对打包模块与 llama/ggml DLL。CUDA 在满足产品声明驱动/运行库的 GPU 机测试；无 GPU 或未提供模型则该行 blocked，而不是 CPU通过代表CUDA通过。保留现有轻量 `--smoke-test`，不让它隐式下载模型或访问 Keyring真实条目。

### D17-Q01 · question · 严重度 null · 跨变体覆盖升级的支持范围未定义

相同 AppId/默认目录允许用户选另一变体覆盖；新包对 sidecars 的 Excludes只限制新来源，代码未显式说明旧文件的清理/模式迁移政策。`is_frozen_standard_variant_without_sidecar` 又以 sidecar/maintenance 存在性判定身份。需要产品/发布维护者明确 embedded→standard、CPU↔CUDA 是支持还是拒绝，才能对残留文件作缺陷判定；目前不能把“必须自动删库/清配置”当要求。

若支持，定义只清理受安装器所有权管理的旧程序资源、保留完整用户数据并显式处理模式；若不支持，在安装前明确拒绝或给出保留数据的迁移流程。回归为两方向×运行/停止×旧新版本；期望由批准政策确定。

### D17-O01 · out_of_scope · P2 · 维护包装器自定义用户名参数交接 D16

安装包会分发的 `.bat/.sh` 在非 postgres 用户时向 dump/restore/maintenance-shell追加 `--username`，README也这样指导；实读 Rust `cli::{DataDirArgs,DumpArgs,RestoreArgs}` 没有该参数。交 D16 对实际分发 sidecar版本/维护实现/既有发现去重确认，不在 D17 重复立功能缺陷或实施修复。默认 postgres 分支不追加参数，不能扩大为“所有离线恢复不可用”。关联回归输入为自定义合法超级用户名，预期 CLI 能接收并使用同一身份；当前未运行。

### D17-O02 · out_of_scope · P2 · platformdirs只在开发锁出现，交D19确认构建闭包

标准库文本核对：pyproject、requirements、requirements-optional 中platformdirs均0处，requirements-dev为4.11.12（via fastmcp-slim/pip-audit）；build-windows只安装前两份及PyInstaller。服务默认路径及维护服务却直接import platformdirs。本轮没有完整审查构建器/第三方hook的全部依赖闭包，不能把“运行锁未列”直接当已经观测到最终包缺模块。交D19核对是否由构建依赖偶然提供、是否必须提升为直接运行依赖，并在干净构建中检验；不重复计为D17确定缺陷。与F02路径契约是不同问题。
