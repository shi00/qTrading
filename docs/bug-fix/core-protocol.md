# AI 问题修复核心协议

> **与项目宪法的关系**：[CLAUDE.md](../../CLAUDE.md) §3 红线（R1~R24）/ §4 架构边界是硬约束；本协议是修复方法论，提供系统化的执行流程。
>
> **冲突优先级**：法律法规 > 已批准需求/契约 > 架构/API/数据契约 > 仓库规则/项目质量门禁 > 本协议通用建议。
>
> **加载方式**：AI 日常只加载本文件；触发 §3 风险信号时 Read [profiles.md](./profiles.md)；需要详细方法/模板/参考实践时 Read [appendix.md](./appendix.md)。
>
> **与检视指南的关系**：本协议与 [docs/reviews/ai-review.md](../reviews/ai-review.md) 互补——检视针对变更质量，修复针对问题解决。

## 1. 核心原则

1.1 **先证据后结论** — 不因报错文本、Issue 描述或用户推测直接定根因；区分事实、假设、推断和待确认信息。
1.2 **先理解后修改** — 修改前理解预期/实际行为、所在层与执行路径、调用方、数据、状态、副作用与信任边界。
1.3 **修根因不掩症状** — 禁止吞错、删断言、跳测试、无依据重试、伪造默认值、关闭门禁制造假成功。
1.4 **最小但完整** — 根因修正 + 回归测试 + 必要 schema/文档/监控同步 + 同类缺陷模式有限检查。
1.5 **验证不宣称** — 实际运行测试/构建/静态检查并报告命令与结果；"应该可以"不等于已修复。
1.6 **保护现场与用户工作** — 不覆盖/回滚/提交用户已有改动；不提交临时文件、日志、凭据和生成物。

## 2. 六状态门执行协议

### S1 调查（Investigate）
- **进入条件**：已接到问题/变更请求或用户授权排查，且问题未归一化。
- **退出条件**：已形成标准问题陈述（目标/预期/实际/范围/严重度/验收/权限边界，模板见 [appendix.md §B](./appendix.md#b-输入契约)）；要素不全且无法从仓库/调用方补齐时不进入 S2，先请求信息或降级到 §4.4。
- 明确预期行为、实际行为、影响范围、严重度、验收标准与权限边界
- 读取项目规则（CLAUDE.md §3/§4）、相关契约、调用方、测试说明
- 检查 `git status`，识别并保护用户已有改动
- 归一化为标准问题陈述（模板见 [appendix.md §B](./appendix.md#b-输入契约)）

### S2 复现（Reproduce）
- **进入条件**：问题陈述已归一化，需要确认问题在受控条件下能否复现。
- **退出条件**：问题已稳定复现（固化为测试/脚本）或间歇问题已记录失败率/时序/资源状态并存档，且满足下方「S2 → S3 判据」之一（以可核对判据取代原「置信度足以支持 S3」的定性判断）。**无法复现时不盲改**：停在 S2/S3，走 §4.4 部分交付（仅诊断/待补充证据），不进入 S4。
- 优先固化为自动化测试、可重复脚本或最小样例
- 间歇问题记录失败率、并发度、时序、随机种子与资源状态
- 无法复现时不盲改：对比正常/异常环境、增加可移除诊断、收窄触发条件、声明当前置信度
- 禁止用反复试改代码代替诊断

**S2 → S3 判据**（满足其一即允许进入 S3 定因）：

| 判据 | 可核对信号 |
|------|-----------|
| 稳定复现 | 有可重复执行的复现命令与失败输出/断言（重复执行结果一致） |
| 间歇复现 | 已量化失败率（观测次数 / 复现次数）并记录时序与资源状态 |
| 无法复现 | 已收窄触发条件、记录已排除的环境差异，且日志或堆栈可定位到具体「文件:符号」 |

### S3 定因（Diagnose）
- **进入条件**：已有复现证据或足够观测信息支撑假设检验。
- **退出条件**：因果结论能解释全部关键症状、触发条件与逃逸原因，且有代码/运行时/实验依据；证据不足时不进入 S4，先补证据或降级到 §4.4。
- 假设驱动：维护假设账本（模板见 [appendix.md §A.1](./appendix.md#a1-假设账本模板)），每次只检验一个主要变量
- 区分症状、直接原因、关键因果因素、促成因素、逃逸原因（五要素见 [appendix.md §A.2](./appendix.md#a2-因果分析五要素)）
- 因果结论须能解释全部关键症状、触发条件与逃逸原因，且有代码/运行时/实验依据
- 不强求唯一根因，不以"人为失误"作为分析终点

### S4 修复（Fix）
- **进入条件**：根因已确诊且有稳定失败证据。
- **退出条件**：最小完整修复已实施且未扩大范围；根因未确诊或缺失败证据时不进入 S4（回到 S2/S3）。
- **先建立失败证据**：新增或确认能稳定失败的测试，在未修复代码上运行确认失败
- 实施最小完整修复：只改根因与必要验证相关文件，遵循现有架构、类型、错误处理与命名约定
- 禁止为让测试通过而削弱断言、标记跳过、过度 mock 或改测试迎合实现
- 发现无关缺陷记录为范围外风险，不擅自扩大修复

### S5 验证（Verify）
- **进入条件**：修复已实施，需要产生风险相称的验证证据。
- **退出条件**：分层验证完成、反证已核对、无法执行的检查已披露；验证未通过或无证据时不进入 S6（回到 S4）。
- 分层验证（从快到慢）：目标复现 → 回归测试 → 邻近测试 → 静态检查 → 构建验证 → 集成/E2E → 全量回归 → 目标环境
- 验证范围由影响面决定，不能只跑新增测试，也不无理由跑全量
- **反证**：原复现是否偶然通过？测试是否真经修复路径？是否只解一个样例？是否破坏上下游契约？是否引入新的安全/注入/数据泄露风险？
- 无法执行的检查须写明：未执行项、原因、替代证据、待人工确认风险

### S6 交付（Deliver）
- **进入条件**：验证证据充分且完成判定可成立。
- **退出条件**：交付状态与残余风险准确披露；未标明的未验证项不视为交付完成。
- 已完成与未验证分开报告，不混淆
- 至少说明：根因+证据、修复内容+机制、变更文件+影响范围、已运行验证+结果、未验证项+残余风险+人工待办
- 高影响或重复问题：搜索同类缺陷模式、更新测试/规则/监控、记录根因+促成+逃逸、固化到 CI 或自动化门禁

## 3. 风险信号 → 专项 Profile 触发表

| 风险信号 | 必须读取 [profiles.md](./profiles.md) 章节 |
|---------|-------------------------------------------|
| 测试失败（含 flaky） | §1 测试失败 |
| 构建/依赖/环境问题 | §2 构建、依赖和环境 |
| 性能下降 | §3 性能 |
| 并发/间歇/竞态 | §4 并发和间歇 |
| 数据写入/迁移/回填 | §5 数据与迁移 |
| 安全/隐私/凭据 | §6 安全 |
| 外部依赖不可用 | §7 外部服务与生产环境不可用 |
| 生产事故 | §8 生产事故（特殊顺序） |

多个信号同时出现时组合读取，不得只选最熟悉的一项。

### 生产事故模式（profiles §8 与六状态门的允许重排/并行映射）

触发「生产事故」风险信号后，止损优先顺序优先于常规六状态门顺序。此时允许按 [profiles.md §8](./profiles.md#8-生产事故特殊顺序) 对 S1~S6 做重排/并行，不完全受 §2 顺序与「完成判定」常规「S1~S6 无跳步」约束：

| profiles §8 步骤 | 对应六状态门（允许重排/并行） |
|------------------|-------------------------------|
| 检测与定级 | S1 调查（定级并入影响/严重度/权限评估） |
| 限制影响（止损） | 优先级最高，可先于 S2/S3 对必要缓解动作执行处置（动机归入 S4） |
| 保存证据 | 与止损并行，S2 现场保护（未保存证据前不重启/清理/覆盖现场） |
| 建立时间线 | S1 调查（时间线并入标准问题陈述） |
| 诊断根因 | S2 复现 + S3 定因（可与止损并行，不因追根因延误必要止损） |
| 安全修复 | S4 修复 |
| 分阶段验证 | S5 验证 |
| 复盘与预防复发 | S6 交付（附无责复盘记录） |

- **允许重排**：止损（限制影响）可越过 S2/S3 提前执行必要处置；证据保存可直接并行，不必等复现完成。
- **完成判定**：触发本模式后，完成判定按「已按 §8 等价完成并标注生产事故模式」执行，而非常规「S1~S6 无跳步」；仍须满足止损已实施、证据已保存、无责复盘已随交付给出。

## 4. 状态门判定

### 4.1 可完成交付（同时满足）
问题与验收标准明确；根因有足够证据；最小完整修复已实施；风险相称的回归已通过；未引入安全/数据/兼容性退化；已披露限制与残余风险。

### 4.2 应停止并请求信息/决策
权威需求或契约冲突；缺少会实质改变方案的产品/架构决策；无法区分目标改动与用户已有改动；多方案存在不可替代的用户决策权衡；必要步骤需未获授权的生产/数据写入。

### 4.3 应升级人工专家
正在利用的安全漏洞/监管/重大隐私事件；可能不可逆数据损坏；需生产紧急变更或大规模回滚；根因跨多团队/供应商且证据冲突；AI 无法安全获得必要环境/权限/专业判断。

### 4.4 允许部分交付（须准确标注状态）
仅诊断完成 / 临时缓解完成永久修复待办 / 代码修复完成目标环境验证待办 / 无法判断需补充指定证据。

## 5. 反模式快速自查

- 吞错、删断言、跳测试、关闭门禁制造假成功
- 试错式补丁（连续改多处无法解释原因）
- 只修错误出现位置（异常抛出点 ≠ 根因）
- 症状缓解冒充根因修复（重启、清缓存、扩大重试）
- 修改测试迎合实现
- 过度修复（借机重构、升级依赖、改公共接口）
- 只跑局部测试，不检查调用方与契约
- 无证据宣称完成（"应该可以""逻辑上没问题"）
- 泄露现场（完整日志、数据、截图、`.env` 入库，或清理了事故证据）

---

## 完成判定（canonical 入口）

- 常规：六状态门（S1~S6）已按序走完：调查→复现→定因→修复→验证→交付，无跳步；或已按「生产事故模式」经 §8 等价完成并标注模式
- S5 验证有证据支撑（复现步骤/通过的用例），S6 交付状态准确
- 满足「4.4 允许部分交付」时已按状态门准确标注，未虚报完成

_最小验证命令：_ 修复涉及的数据层/策略层按 CONTRIBUTING「变更类型 → 最小验证子集」运行对应最小子集；文档改动 → `python scripts/check_docs_consistency.py`。
