# Flet 桌面 UI/UX 最佳实践

> 面向 AStockScreener 的页面信息架构、布局、组件选择和桌面交互设计规范。
>
> **职责边界**：本文只回答“界面应如何设计”，不重复 API、架构红线、无障碍条款或项目踩坑。
> 实现分别遵守 [`v1-api-constraints.md`](./v1-api-constraints.md)、
> [`accessibility-baseline.md`](./accessibility-baseline.md) 和
> [`project-differences.md`](./project-differences.md)。
>
> 文档入口：[Flet 开发文档入口](./README.md)
> Owner: UI 维护者
> 复核触发器: Flet 依赖版本变化、官方设计指南重大变化、目标平台变化、ADR 决策（见 [../adr/](../adr/)）

## 1. 规则等级与来源

本文使用以下等级，未标注的说明文字不构成独立规则：

- **[必须]**：来自项目红线、现行项目契约或无障碍基线，不满足即不得交付。
- **[建议]**：来自官方指南或成熟 UX 实践；没有明确反例时应遵守。
- **[可选]**：依赖页面任务、数据密度或用户群体，可按证据采用。

来源及适用范围：

- [`CLAUDE.md`](../../CLAUDE.md)、[`CONTRIBUTING.md`](../../CONTRIBUTING.md)：
  项目红线、架构和交付要求，优先级最高。
- [Material Design 3](https://m3.material.io/)：布局与组件语义。
- [Flutter 自适应设计最佳实践](https://docs.flutter.dev/ui/adaptive-responsive/best-practices)：
  按可用空间布局、避免占满宽屏、支持多种输入及窗口变化时保持状态。
- [Flet `ResponsiveRow` 官方文档](https://docs.flet.dev/controls/responsiverow/)：
  响应式栅格能力。具体 API 仍以项目锁定版本及 [`mcp-usage.md`](./mcp-usage.md) 核验结果为准。
- [WCAG 2.2](https://www.w3.org/WAI/WCAG22/)：无障碍原则；项目可执行条款统一收口在
  [`accessibility-baseline.md`](./accessibility-baseline.md)。

规则来源映射：

- §3.1、§3.2、§7 的可用空间、宽屏、多输入和状态保持建议来自 Flutter 官方自适应指南。
- §4 的组件语义以 Material Design 3 为依据。
- §8 的强制项来自项目现行契约与无障碍基线。
- §2、§5、§6、§9 是成熟 UX 启发式规则，除非同时引用项目契约，否则不视为官方硬性要求。

Flet 使用 Flutter 渲染，但 Flet Python API 不等同于 Flutter Widget API。Flutter 文档在本文中只作为
设计原则来源，不能直接作为 Flet API 依据。

## 2. 页面信息架构

### 2.1 先任务、后布局

**[建议]** 设计页面前先明确：

- 页面唯一的主要任务是什么；
- 用户进入页面时最先需要看到什么；
- 完成任务所需的最短操作路径；
- 哪些信息只在异常或高级场景出现；
- 完成、失败和取消后用户会到哪里。

**[建议]** 不能用更多 Card、Tab 或 Dialog 代替信息架构。无法用一句话描述主要任务的页面，应先拆分职责。

### 2.2 页面层次

**[建议]** 页面按需要从以下层次组织，不要求每页全部具备：

1. **应用外壳**：全局导航、页面标题和全局状态。
2. **页面工具区**：筛选、搜索、范围选择和主要操作。
3. **主要内容区**：表格、列表、图表、表单或详情。
4. **上下文操作区**：仅对当前选择对象生效的操作。
5. **临时反馈层**：Dialog、SnackBar、Banner 等。

**[建议]** 同一视觉区域保持一个清晰的主要操作；存在多个同等重要任务时可以并列，但应避免制造虚假的优先级。
辅助操作降低视觉权重，危险操作与普通操作保持距离。

### 2.3 渐进披露

- **[建议]** 默认展示完成主要任务所需的信息。
- **[可选]** 高级参数放入可展开区域、次级页面或明确命名的设置区域。
- **[必须]** 关键操作不能只有右键、悬停或双击入口。
- **[必须]** 窄布局可以折叠次要操作，但不得移除核心操作入口。

## 3. 布局与响应式

### 3.1 根据可用空间布局

- **[建议]** 根据实际可用宽度决定布局，不根据“电脑、平板、手机”等设备名称分支。
- **[必须]** 项目栅格、断点和设计令牌遵守
  [`v1-api-constraints.md`](./v1-api-constraints.md) 的响应式契约，不在本文重复具体 API。
- **[必须]** 窗口缩放、文本扩展和内容增长后，核心内容与操作仍然可用。

### 3.2 宽屏不是简单拉伸

- **[建议]** 表单、说明文字和阅读型内容限制合理最大宽度，避免超长行。
- **[建议]** 表格、图表和时间轴可优先占用剩余空间。
- **[建议]** 宽度增加时优先考虑重排、增加栏位或主从布局，而不是同比放大所有控件。
- **[建议]** 不为填满屏幕而制造无意义 Card、空图表或装饰元素。

### 3.3 内容流与滚动

- **[建议]** 优先使用浅层、可读的布局结构。
- **[必须]** 工具区换行或内容增长时，主要内容不能被压缩到不可用。
- **[建议]** 每个方向保持清晰的主要滚动区域，避免相互争夺滚轮和焦点的嵌套滚动。
- **[可选]** 固定工具区、表头或摘要区，但不得显著挤压主要内容。

具体布局机制与已验证陷阱见 [`project-differences.md`](./project-differences.md)，本文不重复维护。

### 3.4 间距与对齐

- **[必须]** 复用项目已有设计令牌，不在页面中另建无依据的视觉体系。
- **[建议]** 同级元素使用一致间距；层级变化通过间距、字号和字重共同表达。
- **[建议]** 表单标签、输入控件和操作按钮保持稳定对齐。
- **[建议]** 数据列按语义对齐：文本通常左对齐，数值通常右对齐，状态和短标签可居中。

## 4. 组件选择

### 4.1 操作按钮

- **[建议] 主要按钮**：用于当前最重要、最常执行的动作。
- **[建议] 普通按钮**：用于重要但非主要的动作。
- **[建议] 文本按钮**：用于取消、返回和低优先级操作。
- **[建议] 图标按钮**：只用于含义稳定、用户熟悉的动作；可访问名称遵守无障碍基线。
- **[必须] 危险按钮**：明确影响对象和范围；不可逆操作需提供确认或可撤销机制。

**[建议]** 按钮文案使用“动词 + 对象”，如“保存策略”“删除记录”，避免脱离上下文的“确定”“处理”。

### 4.2 选择控件

- **[建议]** 单个立即生效的设置使用 Switch。
- **[建议]** 需要随表单统一提交的布尔值使用 Checkbox。
- **[建议]** 少量互斥选项使用 Radio；选项较多或空间受限时使用 Dropdown。
- **[建议]** 多选使用 Checkbox 列表或明确支持多选的组件，不用多个 Switch 模拟多选。

上述选择是 UX 启发式规则，不是控件 API 契约；具体属性和事件以
[`v1-api-constraints.md`](./v1-api-constraints.md) 为准。

### 4.3 导航

- **[建议]** 全局导航只承载产品主要区域，不混入当前页面操作。
- **[建议]** Tabs 只用于同一上下文中的并列内容，不作为任意深度路由系统。
- **[建议]** 用户能从标题、选中状态或路径信息判断当前位置。

#### 导航深链协议（TOPIC_NAVIGATE，UX-01 / UX-04）

跨视图导航统一走 PubSub `TOPIC_NAVIGATE` 单通道，消息格式为 `"<tab>"` 或 `"<tab>:<subtab>"`：

| 消息 | 行为 |
|------|------|
| `"settings"` | 切换到 settings 主 tab（向后兼容） |
| `"settings:data"` | 切换到 settings 主 tab 并激活 data 子页（深链） |
| `"settings:<未知子页>"` | warning + 降级为仅切主 tab（不吞导航） |
| `"screener"` | 切换到 screener 主 tab（向后兼容） |
| `"screener:<code>"` | 切换到 screener 主 tab 并填充股票代码过滤（UX-04 深链，`<code>` 为任意非空字符串） |
| `"<其他 tab>:<subtab>"` | warning + 子页段忽略（仅 settings/screener 定义 subtab 语义） |
| `"a:b:c"` / 空段 | warning + 整体忽略 |

- 合法 settings 子页 key：`data` / `database` / `ai` / `tasks` / `notify` / `system`（单一事实源：`ui/views/settings_view.py` 的 `SETTINGS_SUBTAB_INDEX`，从 `_TAB_CONFIG` 派生，与 `EIDS.SETTINGS.tab` role 对齐）。
- subtab 段语义由目标 tab 定义：settings 段为白名单子页 key；screener 段为股票代码（任意非空字符串，无白名单）。解析层不感知语义差异，仅按 tab 分派。
- 发送方示例：`page.pubsub.send_all_on_topic(TOPIC_NAVIGATE, "settings:data")`（见 `home_view._navigate_to_data_source`）、`send_all_on_topic(TOPIC_NAVIGATE, "screener:600000")`（见 `home_view._on_view_stock` / `watchlist_view._on_view_stock`）。
- 实现约束（Flet hooks 语义）：订阅 handler 是订阅时闭包，内部 state 读取是 stale 的——`AppLayout._on_navigate` 内禁止读取 state 当前值做逻辑判断，state 写入必须用函数式更新（seq 递增防重复深链失效）；子页激活经 `SettingsView` 的 `target_subtab=(key, seq)` prop + `use_effect(dependencies=[target_subtab])` 应用；screener 过滤填充经 `ScreenerView` 的 `stock_filter_request=(code, seq)` prop + 同构 `use_effect` 应用。
- 扩展新页面子页时：以同一协议扩展（key 表与消费方 prop 同步新增），不新增 PubSub topic。

### 4.4 反馈组件

- **[必须] 字段错误**：紧邻字段显示，说明如何修正。
- **[建议] SnackBar**：用于短暂的成功、失败或撤销反馈，不承载必须阅读的信息。
- **[建议] Banner**：用于重要、持续、但不必立即阻断的问题。
- **[建议] Dialog**：用于需要用户立即决定的阻断任务、确认或少量聚焦输入。
- **[建议] 页面内错误状态**：主要内容无法加载时提供重试、修改输入或返回入口。

**[建议]** 不为普通成功操作弹出阻断式 Dialog。后台任务开始后持续显示可观察的运行状态。

### 4.5 数据展示

- **[建议]** 连续、可比较的数据使用表格；异构对象或摘要信息使用列表或 Card。
- **[建议]** Card 只表示独立对象或一组强相关内容，避免“万物 Card 化”。
- **[必须]** 表格提供清晰表头。
- **[建议]** 排序、筛选和选中状态可见；数字统一精度、单位和千分位规则，空值与零值不混淆。
- **[必须]** 图表提供标题、单位、时间范围以及图例或可替代文本摘要。

## 5. 表单设计

- **[建议]** 字段顺序与用户完成任务的自然顺序一致。
- **[必须]** 必填、格式和范围规则在输入附近说明。
- **[建议]** 在字段失焦或提交时提供具体校验，不静默修正用户输入。
- **[建议]** 提交失败后保留用户输入，并明确指出首个错误。
- **[建议]** 提交期间防止重复提交，同时显示正在处理。

字段 label、焦点和键盘路径统一遵守 [`accessibility-baseline.md`](./accessibility-baseline.md)，本文不重复条款。

## 6. 页面状态必须完整

**[建议]** 每个数据驱动页面按适用场景设计并验证：

1. **初始状态**：尚未操作时告诉用户可以做什么。
2. **加载状态**：显示正在进行的任务，避免无反馈等待。
3. **空状态**：解释为什么为空，并提供可执行的下一步。
4. **成功状态**：展示结果和必要的后续入口。
5. **错误状态**：使用可理解的信息说明问题，提供重试、修改输入或返回入口。
6. **部分可用状态**：已有内容保持可用，并清楚标出失败或过期部分。
7. **禁用状态**：说明为什么不可用；不能只显示灰色控件而无原因。

**[建议]** 加载时不无故清空已有结果。刷新失败时优先保留旧数据，并清楚标明数据状态。

## 7. 桌面交互

- **[必须]** 核心流程可由鼠标和键盘完成，细则见无障碍基线。
- **[可选]** 高频操作提供快捷键，但快捷键不能成为唯一入口。
- **[必须]** Hover、右键和双击只能作为加速方式，不能承载唯一功能。
- **[建议]** 滚轮作用于指针所在的可滚动区域，避免滚动页面时意外修改数值字段。
- **[建议]** 窗口缩放后保持当前任务、选择和输入，不因布局切换丢失业务状态。

## 8. 无障碍、国际化与实现边界

- **[必须]** 无障碍设计完整遵守 [`accessibility-baseline.md`](./accessibility-baseline.md)；
  对比度、label、tooltip、错误可读性和键盘路径只在该文档维护。
- **[必须]** 文本缩放及中英文长度变化后，关键内容和操作仍然可用。
- **[必须]** Flet 声明式实现、i18n 状态和异步行为遵守
  [`v1-api-constraints.md`](./v1-api-constraints.md) 与 [`CLAUDE.md`](../../CLAUDE.md)。
- **[建议]** 大数据页面保持可交互并提供可观察反馈；分页、虚拟化和性能实现根据实际测量决定。

本文不规定 API、线程池、ViewModel、取消传播或布局属性的具体写法。

## 9. 常见反模式

- **[建议避免]** 根据设备名称或操作系统猜测可用宽度。
- **[建议避免]** 大量固定宽高造成缩放溢出或宽屏空洞。
- **[建议避免]** 用无意义 Card、空白控件或装饰元素修补信息层级。
- **[建议避免]** 多个操作同等强调，用户无法判断下一步。
- **[建议避免]** 只设计正常结果，遗漏加载、空数据和失败状态。
- **[建议避免]** 用 Dialog 展示普通通知，或用 SnackBar 承载必须确认的信息。
- **[必须避免]** 依赖颜色、悬停、右键或双击作为唯一信息或操作入口。

## 10. 开发流程

新增或显著修改页面时：

1. 写出主要任务、主要操作和完成路径。
2. 列出初始、加载、空、成功、错误及部分可用状态。
3. 先确定信息层级和交互路径，再选择组件。
4. 在最小窗口、常用窗口和最大化窗口下验证布局。
5. 使用长文本、空数据、大数据和错误响应验证边界。
6. 按 [`accessibility-baseline.md`](./accessibility-baseline.md) 检查无障碍。
7. 按 [`v1-api-constraints.md`](./v1-api-constraints.md) 和项目门禁验证实现。

## 11. PR 评审清单

### 信息架构

- [ ] 页面主要任务、完成路径和操作优先级清晰。
- [ ] 全局导航、页面操作和对象操作没有混在一起。
- [ ] 高级内容采用渐进披露，但关键操作没有被隐藏。

### 布局

- [ ] 最小宽度、最大化、长文本和内容增长下布局均可用。
- [ ] 宽屏内容没有无意义拉伸，主要内容不会被工具区挤压。
- [ ] 滚动边界清晰，没有相互争夺输入的滚动区域。

### 组件与状态

- [ ] 组件语义符合 Material 组件用途。
- [ ] 按钮层级、文案和危险操作清晰。
- [ ] 初始、加载、空、成功、错误和部分可用状态已覆盖。
- [ ] 表单校验具体，失败后不丢失用户输入。

### 桌面体验

- [ ] 鼠标、键盘、窗口缩放和长文本场景可用。
- [ ] Hover、右键、双击和快捷键都不是唯一入口。
- [ ] 窄布局没有隐藏核心操作。

无障碍和工程实现不在此重复列项，分别使用
[`accessibility-baseline.md`](./accessibility-baseline.md) 与
[`v1-api-constraints.md`](./v1-api-constraints.md) 的检查清单。

## 12. 维护边界

- 本文只维护 UI/UX 设计决策、启发式规则及 UX 评审清单。
- API 变化更新 `v1-api-constraints.md`；项目踩坑更新 `project-differences.md`；
  无障碍条款更新 `accessibility-baseline.md`，不得复制到本文。
- 新增规则必须标注等级；外部规则应给出官方来源，项目经验应链接项目证据。
- Flet 依赖升级、官方设计指南重大变化或目标平台变化时复核本文。
- 与红线或专项规范冲突时，以更高优先级文档为准，并修正本文。
- 文档导航与任务路由只在 README.md 维护，本文不复制专题清单。
